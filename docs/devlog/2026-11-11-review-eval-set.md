## 바로잡은 것

- **자료 파일을 낱말 바꾸기로 만들어 규칙 본문까지 바꿨다:** 두 번째 사례의 자료 파일을 첫 사례 것에서 「PR #32」를 「PR #28」로 바꿔 만들자 `REVIEW.md` 본문의 사례 번호까지 바뀌었다. 리뷰어를 띄우기 전에 `REVIEW.md` 부분을 원문과 비교해 찾았다. 틀에서 새로 만들고 비교하는 줄을 스킬과 가이드에 넣었다.
- **평가가 도는 중에 규칙 폴더의 `REVIEW.md`를 고쳤다:** 두 번째 사례의 리뷰어가 돌기 시작한 직후 이 PR에 넣을 한 줄을 먼저 썼다가 30초쯤 뒤 되돌렸다. 리뷰어는 자료 파일의 사본을 받았고 리뷰 기준과 상관없는 줄이었다. 세 사례를 마친 뒤 다시 넣었다. 가이드에 「평가가 도는 동안 규칙 파일을 고치지 않는다」를 적었다.
- **준비하다 사용자 저장소에 임시 ref를 만들었다:** 사례 셋의 PR 머리를 받으려고 원래 저장소에 `refs/remotes/eval-tmp/*`를 만들었다가 바로 지웠다. 스킬의 평가 모드는 임시 클론만 쓰고 사용자 저장소에 worktree, 브랜치, ref를 만들지 않게 적었다.
- **임시 클론을 `--filter=blob:none`으로 받아 git 이력 리뷰어가 막혔다:** 첫 사례에서 `git log -S` 일부가 끝까지 돌지 못했다. 세 사례를 같은 스킬 판으로 재려고 그대로 돌린 뒤, 스킬을 보통 클론으로 고쳤다.
- **스킬을 고친 세션의 Skill 도구가 옛 판을 보여 줬다:** 스킬 파일을 두 번 바꿔 넣은 뒤 Skill 도구가 첫 번째 판을 보여 줬다. 디스크 파일을 따라 돌리고 sha를 적었다. 스킬에 그 줄을 넣었다.

## 검증

- 기준 시험: 고치기 전 스킬을 새 에이전트에게 읽혀 `28 --eval --at …`을 물었다. 「이미 리뷰가 있어 1번에서 멈춘다, 이어 가면 10번에서 `gh pr comment`, 리뷰어는 마지막 머리를 본다」고 답했다.
- 고친 뒤: 같은 질문과 `--eval` 없는 경우를 물었다. 평가 모드는 의도대로 읽혔고 기본 동작은 그대로라고 답했다. 짚은 애매한 곳 둘(평가 모드가 바꾸는 단계 목록, 고친 기록이 없는 본문)을 고쳤다.
- 고치기 전 백업과 마지막 판의 diff에서 기본 동작 쪽 hunk는 넷(설명 줄, 평가 모드를 가리키는 문단, 1번과 10번의 한 줄)이고 지운 줄은 고쳐 쓴 둘뿐이다.
- 평가 실행:

  | PR | 기대 | 결과 | 에이전트 | 걸린 시간 |
  |---|---|---|---|---|
  | #32 | 잡아야 함 | 잡음, final 95(raw 75) | 14 | 8.6분 |
  | #28 | 잡아야 함 | 잡음, final 95(raw 75) | 16 | 8.0분 |
  | #26 | 걸러야 함 | 거름, 리뷰어가 올리지 않음 | 15 | 7.0분 |

- 세 PR의 이슈 코멘트, 리뷰, 리뷰 코멘트 수가 처음과 끝에 같았다(각 1, 0, 0).
- push 전에 `git log -p origin/main..HEAD`를 다시 읽었다. 가이드의 「후보는 비공개 메모의 할 일 파일에 있다」(할 일 04는 공개 파일이다)와 재지 않은 「점수는 한 단계쯤 흔들린다」를 고쳐 처음 커밋에 합쳤다.
