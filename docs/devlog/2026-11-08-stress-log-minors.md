## 한 일

PR #61 리뷰에서 미룬 다섯을 고쳤다. 맥에서 손으로 돌리는 스크립트라 맥 서버의 동작은 바뀌지 않는다.

1. 특징 스크립트가 재지 못한 파일은 그 파일만 실패로 세고, 같은 묶음의 나머지는 잰다. 실패한 파일은 다음 실행에 다시 잰다.
2. 실패를 단계(wav, mfa align, stress features)별로 센다. MFA를 돌리기 전에 MFA 환경이 parselmouth와 praatio를 불러오는지 본다.
3. 값 파일에 역할극을 만든 때(`created`)를 남기고, `--since`는 녹음한 때, 만든 때, 잰 때의 차례로 거른다.
4. 「확실도 위 25%」의 사분위수를 `inclusive`로 잡는다.
5. `JE_DATA_DIR`에 `roleplays/`가 없으면 두 스크립트 모두 아무것도 만들지 않고 멈춘다.

## 바로잡은 것

- **앱 PR을 고치는 동안 이 브랜치의 시험을 임시 커밋으로 두었다.** main 세션이 PR #63의 충돌을 풀어 달라고 했을 때, 쓰던 시험을 임시 커밋으로 두고 브랜치를 옮겼다(공유하는 stash는 쓰지 않았다). 첫 임시 커밋은 첫 줄이 73자라 훅에 막혔는데, 이번에는 `&&`로 이어 브랜치를 옮기지 않고 멈췄다. 돌아와서 임시 커밋을 되돌렸고 push하지 않았다.

- 브랜치 최종 리뷰(머지해도 됨, 작은 것 일곱): 고친 것은 다음과 같다.
  - 늘 같은 식으로 실패하는 파일은 실행마다 다시 재는데, 어느 파일인지 알 수 없었다. 특징 스크립트가 재지 못한 시도를 역할극 ID, 줄, 시도 번호로 찍는다(낱말과 경로는 아니다). 가이드에 「실행마다 같은 시도가 찍히면 그 녹음을 보고 코드를 고친다」를 적었다.
  - MFA 환경에 `bin/python`이 없으면 `features_ready`가 경로가 든 오류를 냈다. `OSError`를 잡는다.
  - 가이드의 「실패한 녹음」 두 줄이 서로 다른 뜻(`failed`, `unaligned`)이라 헷갈렸다. 찍히는 이름으로 썼다. 「첫 표의 숫자는 그대로다」를 「같은 70개를 두 방법으로 견주니」로 고쳤다.
  - 스펙의 「출력은 개수와 걸린 시간만」에 단계 이름과 시도를 더했다.
  - 시험을 더했다: 특징 단계가 통째로 실패할 때, 여러 단계가 찍힐 때, `features_ready`의 진짜 함수(가짜 `python`으로), 낱말 하나일 때의 확실도 위 25%(그 낱말).
- 남긴 것: `created`가 없는 옛 값 파일을 `roleplay.json`에서 날짜를 찾아 채우는 것은 하지 않았다. `stress/`를 지우고 다시 재면 되고(5분쯤), 가이드에 적었다.

## 검증

- `cd server && uv run pytest`: 669개 통과(`JE_MFA_ENV`를 주어 특징 스크립트 시험도 MFA 환경에서 돌렸다). 처음 새 시험 16개(시험 이름 기준)를 옛 코드에 돌려 모두 실패하는 것을 봤다. 넷은 새 함수가 없어 준비 단계에서 오류였다. 최종 리뷰 뒤에 더한 시험 셋(시도 찍기, `features_ready`, 낱말 하나)도 고치기 전에 실패하는 것을 봤다.
- 실제 기록의 사본(맥 앱 데이터 폴더의 `roleplays/`와 `stress/`를 복사, 녹음 70개의 값):
  - 옛 표와 새 표: 「다르게 말한 영어」의 확실도 위 25% 줄만 2낱말에서 3낱말로 바뀌었다. 가이드 첫 표의 숫자는 그대로다.
  - 새로 잴 녹음은 없었다(`measured 0`). 값 파일 셋을 지우고 다시 재어 `measured 3, failed 0`(83초). 새 값 파일에 `created`가 들어갔고, 사본의 `tmp/`는 비었다. 다시 낸 표의 숫자는 같았다.
  - 없는 폴더를 `JE_DATA_DIR`로 주면 두 스크립트 모두 종료 1로 멈추고 폴더를 만들지 않았다.
  - 원래 기록과 값은 재기 전과 뒤의 체크섬이 같았다. 사본은 끝나고 지웠다.
