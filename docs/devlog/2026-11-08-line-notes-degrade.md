## 한 일

- 원인부터 갈랐다. 실제 대사 61줄에 서버와 같은 첫 요청을 한 번씩 보내고 답을 저장소 밖에 남겨, 걸린 이유를 하나씩 봤다. 걸린 것의 대부분은 지시문이 아니라 검사 탓이었다.
- 읽는 법의 한글 소리(`[[…]]`)는 한글 글자만 맞추게 했다. 하이픈 위치, 낱말 사이 띄어쓰기, 음절 안의 센 글자 하나만 가리키기는 이제 걸리지 않는다.
- 모델이 센 음절 표시에서 받침을 빼거나 모음만 준 것을 서버가 검사 전에 맞춘다(`threeline.tidy`).
- 낱말을 빼먹은 답을 다시 물을 때 무엇이 어디서 빠졌는지 적는다.
- 목록 대본과 「이 상황 다시 하기」는 한글이나 설명이 빠진 읽는 법을 가져오지 않고 다시 만든다(`threeline.settled`).
- 맥 기록의 줄로 서버의 `Claude.annotate`를 그대로 불러 재는 스크립트를 더했다(`server/scripts/check_three_lines.py`).
- 지시문과 앱은 바꾸지 않았다.

## 바로잡은 것

- **맥 기록에서 본 낱말을 「made-up」이라 적었다:** 진단 답에서 본 한글 조각(모델이 실제 대사에 쓴 것)을 계획, 시험, 커밋 메시지 둘에 예로 쓰고 「made-up」이라고 적었다. 가이드를 쓰기 전에 알아챘다. 아직 push 전이라, 브랜치를 훅을 거치는 보통 커밋으로 다시 쌓아 새로 지어낸 예로 바꿨다. 옛 커밋과 새 커밋의 차이가 예 바꾼 곳뿐인 것을 diff로 확인했다. 진단 답을 본 뒤에는 거기 나온 낱말을 예로 쓰지 않고 새로 지어낸다. 가이드 「덜 된 이유를 가르는 방법」에 실제 줄과 답은 비공개이고 예는 지어낸다고 적었다.
- **막힌 커밋 뒤에 완료 기록이 남았다:** 커밋 명령과 작업 기록 줄을 `;`로 이었다. 제목이 73자라 커밋이 막혔는데도 기록에 완료 줄이 들어갔다. 줄을 지우고 다시 커밋하다가 제목만 든 커밋을 만들어, push 전에 메시지를 고쳤다. 커밋과 그 뒤 일은 `&&`로 잇는다.
- **`tidy`가 모음만 봤다(최종 리뷰):** 다른 글자를 가리킨 표시(「스탑」에 「즈」)도 「스」로 바뀌어 검사를 통과했다. 틀린 표시는 표시가 없는 것보다 나쁘다. 리뷰어는 「첫 자음까지 같아야」를 권했지만, 그러면 진단에 있던 「모음만 든 글자」 꼴(「빌」에 「이」)을 놓친다. 그래서 「첫 자음이 같거나 ㅇ」으로 정했다. 진단 답 16건에 대 보니 모두 맞춰졌다.
- **할 일 파일을 PR에 넣지 않았다(최종 리뷰):** 코드와 스펙이 가리키는 할 일이 원래 폴더에만 있었다. 상태를 「완료」로 고쳐 넣고 할 일 3의 답을 적었다.
- **계획 문장을 코드에 맞추지 않았고, 같은 규칙을 여러 곳에 적었다(PR 리뷰 스펙 축):** `tidy`를 좁힌 뒤 계획 Task 3은 옛 문장 그대로였다. 「설명 빠진 읽는 법은 다시 만든다」는 두 스펙과 docstring에 따로 적혀 있었다. 계획을 고치고, 규칙은 목록 대본 스펙 2에만 두고 나머지는 그곳을 가리키게 했다.
- **`REVIEW.md`:** 고치지 않았다. PR 리뷰의 경계선(진단 예에 「지어낸」 표시가 그 자리에 없음)은 점수 단계가 계획과 가이드의 「지어낸 예만 쓴다」 문장을 보고 걸렀다. 표시를 그 자리에 붙여 닫았다.
