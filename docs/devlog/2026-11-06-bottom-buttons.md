## 바로잡은 것

- **고치기 전의 실패를 재는 시험이 처음에는 아무것도 재지 않았다.** 에뮬레이터 화면의 뷰 위치를 `uiautomator dump`로 읽는 일회용 스크립트를 썼다. XML 속성 순서를 잘못 가정해 앱의 뷰를 하나도 찾지 못했는데, 그래도 「실패」가 나왔다. 실패 이유를 출력에서 확인하고 고친 뒤에야 「앱 화면 틀이 2400px(화면 끝)까지 간다」는 진짜 실패를 봤다. 시험이 실패할 때는 실패 이유까지 본다.
- **안내 글의 여백을 잘못 셈했다.** 서버 설정이 없을 때 뜨는 안내 글은 상태 줄을 피하려고 `marginTop: 80`을 두었다. 틀이 상태 줄을 피하게 되면서 이것을 56으로 줄였는데, `StatusBar.currentHeight`의 기본값 24를 상태 줄 높이로 쳤다. 실제 상태 줄은 더 높아서(에뮬레이터에서 약 49dp) 안내 글이 오히려 내려갔다. 리뷰어 6명도 「24 + 56 = 80이라 같다」고 넘겼다. 리뷰 뒤 PR 본문에 「위치는 전과 같다」고 쓰다가 찾았다. `marginTop`을 빼고 사방 여백 24만 남겼다. 상태 줄 높이 같은 기기 값은 코드의 기본값이 아니라 잰 값으로 셈한다. 리뷰 기준에는 넣지 않았다. 이 저장소만의 지적 항목이 아니고, 드물게 보이는 개발용 화면이다.

## 검증

- `cd app && npx tsc --noEmit` → 오류 없음
- `cd app && npx jest` → 98 passed. 화면 틀은 네이티브가 여백을 주는 것이라 jest로 잴 수 없어, 아래 기기 시험으로 확인했다.
- 에뮬레이터(이 브랜치의 릴리스 APK):
  - 세 버튼(`adb shell cmd overlay enable-exclusive --category com.android.internal.systemui.navbar.threebutton`): 아래 줄은 2274~2400px(48dp). 고치기 전에는 앱 화면 틀이 2400px까지 갔고, 고친 뒤에는 128~2274px에서 끝난다(`uiautomator dump`의 bounds와 `dumpsys window`의 navigationBars 비교).
  - 제스처: 아래 줄은 2337~2400px(24dp). 틀이 2337px에서 끝난다. 앱을 다시 띄우지 않아도 방식을 바꾸면 바로 따라 바뀐다.
  - 첫 화면과 상황 화면을 찍어 위쪽(그림, 「뒤로」 위치)이 고치기 전과 같은 것을 봤다.
  - 시험 뒤 에뮬레이터를 제스처 방식으로 돌려 두었다.
- pr-review: 코드 축 0건(경계선 0건). 스펙 축은 표현 차이 2건(PR 본문에 `msg` 변경이 없다, 폰 확인이 남았다)이라 본문에 한 줄 더했다. PR에는 「걸린 것 없음」으로 게시.
