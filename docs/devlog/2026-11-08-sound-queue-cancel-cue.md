## 한 일

- 할 일 42: 앱 뿌리(`App.tsx`)가 내려갈 때 `SoundQueue.close()`를 부른다. 대기열을 비우고 폰의 플레이어를 놓고, 닫은 뒤 들어온 소리는 버린다. 개발 중 다시 깔 때 앱이 한 프로세스에서 두 번 떠, 먼저 뜬 화면이 닫히기 전에 청한 인사가 닫힌 뒤 도착해 울렸다.
- 할 일 43: 취소 소리를 같은 392Hz 한 음에 2배음과 3배음을 섞은 소리로 바꿨다. 폰 스피커에서 시작 소리와의 차이가 11 dB에서 평균 2.4 dB가 됐다.
- 폰 스피커로 나온 알림 소리를 맥 마이크로 재는 방법을 가이드에 남겼다.

## 바로잡은 것

- **저절로 취소를 기다리다 방 소리가 맥에 갔다.** 취소 소리를 내려고 「🎤 말하기」 뒤 5초 저절로 취소를 기다렸는데, 방의 소리가 말소리로 잡혀 녹음이 맥에 가서 받아써지고 라이언 답이 한 번 불렸다. 받아쓴 글은 보지 않고 그 시험 복사본째 바로 지웠다. 두 번째 복사본부터는 「취소」를 직접 눌렀다. 가이드의 재는 방법에 「취소」를 직접 누르라고 적었다.
- **「취소」 버튼을 너무 일찍 찾았다.** 녹음이 켜지기 전에 화면을 읽어 「취소」를 못 찾고 멈췄다(그 녹음은 5초에 저절로 취소됐다). 세 번까지 다시 읽게 고쳤다. 가이드에 적었다.

- **커밋을 `&&`로 잇지 않아 막힌 커밋의 파일이 다음 커밋에 섞였다.** 리뷰 고침을 네 커밋으로 나눠 한 명령에 줄줄이 썼는데, 둘째 커밋이 첫 줄 길이(78자)로 commit-msg 훅에 막히고도 다음 줄이 돌았다. 스테이징에 남은 파일 넷이 가이드 커밋(a42ab0c)에 섞여 push까지 됐다. force push는 하지 않으므로, 그 커밋을 되돌리는 커밋을 두고 같은 내용을 제 메시지로 두 커밋에 다시 넣었다(7529f6d, 46c8942, ffd4f16). PR #60에서 겪고 넘길 글에도 적혀 있던 일이다. 막는 방법은 이미 있는 규칙대로, 커밋 여러 개는 처음부터 끝까지 `&&` 하나로 잇는다.

## 리뷰

- 브랜치 최종 리뷰(With fixes): 대기열을 닫을 때 지금 나는 소리를 멈추는지 시험이 없었다. expo-audio의 `remove()`는 안드로이드에서 플레이어를 목록에서 빼기만 하고 소리를 멈추지 않아, `close()` 안의 `clear()`(멈춤)가 먼저 도는 것이 중요하다. 리뷰어가 순서를 바꿔도 시험이 모두 통과하는 것을 보였다. 시험이 멈춤과 놓기의 순서를 보게 고쳤고, 순서를 바꾼 코드에서 새 시험 둘이 실패하는 것을 봤다. 「놓은 플레이어는 오류를 낸다」는 주석(첫 커밋 본문에도 있다)은 틀려서 고쳤다.
- 같은 리뷰의 작은 것: StrictMode를 쓰지 않는다는 전제를 `App.tsx`에 적었다. 가이드의 소리 표에 배음을 적고, 확인 기준을 「네 번 잰 평균이 3 dB 안쪽」으로 고쳤다. 소리 파일 머리 주석을 고쳤다.
- pr-review(Full, 코드 축 5명과 스펙 축): 50점을 넘은 것이 없어 「걸린 것 없음」으로 게시했다. 경계선(25점) 둘(소리 파일 머리 주석, `Note` 주석)은 고쳤다. 스펙 축의 표현 차이 둘 가운데, 스펙에 남은 「진폭을 반으로」 기록에 취소 소리를 더했고 PR 본문에 평균과 한 번의 3.3 dB를 적었다.
- 남긴 것: StrictMode에서도 버티게 대기열을 효과 안에서 만드는 고침은 하지 않았다(20점, 지금은 StrictMode가 없고 Fast Refresh는 `useMemo`를 다시 돌려 새 대기열을 만든다). 앱이 다시 뜰 때 `prepareCues()`가 옛 알림 플레이어를 놓지 않는 것은 이 PR 전부터이고 에코와 상관없어 두었다.

## 검증
