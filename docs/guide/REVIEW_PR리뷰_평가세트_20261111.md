# REVIEW PR 리뷰 평가 세트

리뷰가 예전에 놓쳤거나 잘 거른 지난 PR에 pr-review 스킬을 다시 돌려, 스킬이나 `REVIEW.md`를 고친 뒤에도 그 문제를 정말 잡는지(또는 거르는지) 잰다. 「How the Claude Code team does code review」(https://claude.dev/blog/solving-code-review-at-anthropic/)의 「How we make the reviewer better」 절에서 가져온 생각이다. 그 팀은 사고를 낸 지난 PR을 모아 리뷰어가 바뀔 때마다 다시 채점한다.

`REVIEW.md` 「고치는 방법」은 리뷰가 놓친 문제를 「반드시 지적할 것」에 규칙으로 옮긴다. 이 세트는 그 규칙이 실제로 리뷰를 바꿨는지 확인하는 쪽이다.

## 언제 돌리나

- pr-review 스킬이나 `REVIEW.md`를 고칠 때
- 리뷰에 쓰는 모델이 바뀔 때

`REVIEW.md` 「고치는 방법」에도 같은 줄이 있다.

## 세트

| PR | 기대 | 보는 `REVIEW.md` 항목 | `--at` (예전 리뷰 때의 PR 머리) | `--asof` (예전 리뷰를 게시한 시각) |
|---|---|---|---|---|
| #32 | 잡아야 함 | 「반드시 지적할 것」의 「공개 저장소 노출」 | `dde02bc8e578fd5e4272727a084fa3ffc76b27c3` | `2026-11-07T16:17:07Z` |
| #28 | 잡아야 함 | 「반드시 지적할 것」의 「앱 화면」 | `2397a19b1a178325298db76d6d73bbbef1c9535a` | `2026-11-07T07:24:33Z` |
| #26 | 걸러야 함 | 「넘길 것」의 첫 항목 | `e12d0c49c07edfdc59d49e66fc09f5863ff9b194` | `2026-11-07T02:30:24Z` |

- 사례마다 무엇을 잡거나 걸러야 하는지(파일, 줄, 내용)는 비공개 메모 `docs/private/review-eval/`에 있다. 사례를 설명하다 보면 기록이나 받아쓰기에서 온 낱말이 다시 들어갈 수 있어서 공개 파일에는 쓰지 않는다.
- 판정:
  - 잡아야 함: 기대한 문제가 코드 축 `final_score` 50 이상으로 남는다(PR 코멘트에 올랐을 것).
  - 걸러야 함: 기대한 지적이 없거나 50 아래다.
  - 같은 PR에서 나온 다른 지적의 점수는 판정에 쓰지 않고 기록만 한다.
- 사례를 늘리는 것은 사용자가 정한다. 후보는 할 일 `docs/todo/20261111_04_todo_pr_review_eval_set.md` 「후보 사례」에 있다.

## 돌리는 법

pr-review 스킬의 평가 모드(`--eval`)로 돌린다. 평가 모드는 닫힌 PR과 이미 리뷰한 PR도 받고, PR에 코멘트를 달지 않는다. 스킬 파일의 「평가 모드」 절이 자세한 단계다.

```
/pr-review 32 --eval --at dde02bc8e578fd5e4272727a084fa3ffc76b27c3 --asof 2026-11-07T16:17:07Z --out docs/private/review-eval/<날짜>-pr32.md
/pr-review 28 --eval --at 2397a19b1a178325298db76d6d73bbbef1c9535a --asof 2026-11-07T07:24:33Z --out docs/private/review-eval/<날짜>-pr28.md
/pr-review 26 --eval --at e12d0c49c07edfdc59d49e66fc09f5863ff9b194 --asof 2026-11-07T02:30:24Z --out docs/private/review-eval/<날짜>-pr26.md
```

- 규칙(`CLAUDE.md`, `AGENTS.md`, `REVIEW.md`)은 스킬을 부른 폴더의 지금 파일을 쓴다. 원래 폴더(main)에서 부르면 main의 규칙으로 잰다. `REVIEW.md`를 고치는 브랜치의 worktree에서 부르면 머지하기 전에 고친 규칙으로 잴 수 있다.
- 사례는 하나씩 차례로 돌린다. 사례마다 걸린 시간을 따로 재기 위해서다.
- 평가가 도는 동안 규칙 폴더의 `REVIEW.md`, `AGENTS.md`, `CLAUDE.md`를 고치지 않는다.
- 쓰는 양: 사례 하나에 에이전트 14~16개(그중 Opus 하나), 7~9분이 걸렸다. 셋이면 에이전트 45개, 24분쯤이다. 돈은 들지 않지만 주간 한도를 쓴다.
- 평가 모드는 PR의 코멘트, 리뷰, 리뷰 코멘트 수를 처음과 끝에 세어 결과에 적는다. 다르면 결과 맨 위에 경고가 붙는다. 지우는 것은 사용자에게 묻는다.

## 결과를 견주는 법

평가 모드는 9번 보고서 아래에 「평가 결과」 블록을 붙인다. 견줄 때 보는 줄은 이것이다.

- 스킬: `SKILL.md`의 sha256 앞 12자. 스킬을 고치면 바뀐다.
- 규칙 폴더의 커밋과, 규칙 파일에 커밋하지 않은 변경이 있었는지
- 코드 축 표에서 기대한 문제의 `raw`, 보정, `final`, 「게시였을지」
- 띄운 에이전트 수와 걸린 시간

아래 「기록」 표에 한 줄씩 더한다. 같은 스킬과 규칙으로 돌려도 점수는 흔들릴 수 있다(같은 판으로 여러 번 돌려 잰 적은 아직 없다). 판정이 전과 달라지면 그 사례를 한 번 더 돌려 확인한 뒤 고칠지 정한다.

## 기록

| 날짜 | 스킬 | 규칙 커밋 | #32 (잡아야 함) | #28 (잡아야 함) | #26 (걸러야 함) | 쓴 양 |
|---|---|---|---|---|---|---|
| 2026-11-11 | `a3129bc932e6` | `472186747163` | 잡음: 75 + 보정 20 = 95 (보정 없이도 75) | 잡음: 75 + 보정 20 = 95 (보정 없이도 75) | 거름: 리뷰어가 「넘길 것」이라며 올리지 않음 | 에이전트 14 + 16 + 15 = 45 (Opus 3), 8.6 + 8.0 + 7.0 = 23.6분 |

- 예전 리뷰(평가 세트 전)에서는 #32가 25점, #28이 45점이라 둘 다 PR 코멘트에 오르지 않았다. 그 뒤 `REVIEW.md` 「반드시 지적할 것」에 두 문제를 이름으로 적었다. #26은 25점으로 걸렀고, 그 뒤 「넘길 것」에 적었다.
- 2026-11-11 판은 스킬 `a3129bc932e6`로 돌렸다. 그 뒤 「겪은 문제와 해결」을 반영해 `81a89798d7d4`로 바꿨다. 바뀐 것은 임시 클론 방식과 기록 방법뿐이고 리뷰어와 점수 프롬프트는 같다. 다음에 돌릴 때 견주는 기준은 이 줄이다.

## 겪은 문제와 해결

### 마지막 PR 머리로 돌리면 고친 코드를 리뷰한다

- 증상: #28은 예전 리뷰가 게시된 1분 뒤에 그 문제를 고친 커밋이 같은 PR에 올라왔다. #32도 리뷰 2분 뒤에 고쳤다. `git fetch origin pull/<N>/head`로 받은 마지막 머리를 리뷰하면 이미 고친 코드를 보게 되어 「잡는가」를 잴 수 없다.
- 고친 것: `--at`으로 예전 리뷰 때의 머리를 준다. 찾는 법은 예전 리뷰 코멘트의 시각과 PR 커밋 목록을 견주는 것이다.
  ```
  gh api repos/<o>/<r>/issues/<N>/comments --jq '.[] | {created_at, head: .body[0:80]}'
  gh pr view <N> --json commits --jq '.commits[] | "\(.oid) \(.committedDate) \(.messageHeadline)"'
  ```
  리뷰 시각 바로 전의 커밋이 그때의 머리다. 커밋 시각은 push 시각과 다를 수 있으니, 바로 뒤 커밋의 제목이 그 리뷰를 고친 것인지도 본다.

### `gh pr diff`와 지금 PR 본문도 그 뒤의 것이다

- `gh pr diff`는 마지막 머리의 diff다. 평가 모드는 임시 클론에서 기준 커밋과 `--at` 커밋의 diff를 만든다.
- 머지된 PR의 머리는 이미 main의 조상이라, main 끝과 merge-base를 구하면 머리 자신이 나와 diff가 빈다. 머지 커밋의 첫 부모(머지 직전의 main)와 견준다.
- PR 본문도 리뷰 뒤에 고쳐진다(#28은 여섯 번). GraphQL `userContentEdits`의 `diff`가 그 판의 본문 전체라, `--asof` 전의 마지막 판을 쓴다.

### 리뷰어가 답을 볼 수 있다

- 그 PR의 예전 리뷰 코멘트, 리뷰 뒤에 고친 커밋, 뒤의 PR을 리뷰어가 읽으면 답을 보고 찾는 셈이다. 평가 모드는 모든 서브에이전트에 「이 PR의 코멘트를 읽지 않는다, `--asof` 뒤의 것을 보지 않는다, git 이력은 임시 클론의 HEAD 조상만 본다」를 붙인다.
- 스킬을 돌리는 세션은 사례의 기대를 안다. 예전 점수나 「무엇을 찾아야 한다」를 서브에이전트 프롬프트에 넣지 않는다.
- 한계: `REVIEW.md` 자체가 사례의 PR 번호와 무엇이 문제였는지를 적고 있다. 그래서 이 세트는 「규칙이 없을 때 리뷰어가 스스로 찾는가」가 아니라 「규칙이 있을 때 그 문제가 점수 단계를 지나 게시까지 가는가」를 잰다. 규칙에 적지 않은 새 문제를 찾는 힘을 재려면 아직 규칙에 옮기지 않은 사례를 세트에 넣어야 한다.

### 자료 파일을 다른 사례 것에서 낱말 바꾸기로 만들면 규칙 본문까지 바뀐다

- 증상: 두 번째 사례의 자료 파일(`REVIEW.md` 전문, 오탐 목록, 루브릭을 모은 것)을 첫 사례 것에서 「PR #32」를 「PR #28」로 바꿔 만들었더니, `REVIEW.md` 본문에 사례로 적힌 「PR #32」까지 바뀌었다. 리뷰어를 띄우기 전에 `REVIEW.md` 부분을 원문과 비교해 찾았다.
- 고친 것: 사례마다 틀에서 새로 만들고, 만든 뒤 `REVIEW.md` 부분이 원문과 같은지 확인한다.

### 임시 클론을 `--filter=blob:none`으로 받으면 git 이력 리뷰어가 막힌다

- 증상: 첫 사례에서 git 이력 리뷰어(4c)의 `git log -S` 일부가 「객체 없음」으로 끝나지 않았다.
- 고친 것: 이 저장소는 7MB쯤이라 보통 클론으로 바꿨다(스킬 「평가 모드」 준비 3, 첫 기록 뒤에 고침). 큰 저장소에서만 필터를 쓰고, 그때는 결과에 그 한계를 적는다.

### 스킬을 고친 세션의 Skill 도구는 고치기 전 판을 보여 줄 수 있다

- 증상: 스킬 파일을 두 번 바꿔 넣은 세션에서 Skill 도구로 부르자 첫 번째 판의 글이 나왔다. 실제 파일은 두 번째 판이었다.
- 고친 것: 스킬을 고친 세션에서 평가를 돌릴 때는 디스크의 `SKILL.md`를 따르고, 결과의 「스킬」 줄에 디스크 파일의 sha256을 적는다. 새 세션에서 돌리면 이 문제가 없다.

### 7번 보정 하나는 오케스트레이터의 판단이 섞인다

- 「PR 자신의 문서, 가이드, 코드 주석이 그 꼴을 금지하면 +10」은 무엇을 「PR 자신의」 글로 볼지에 따라 점수가 10 달라진다. 이번에는 「PR이 더하거나 고친 파일의 글」로 봤다(#32는 그 PR이 더한 가이드, #28은 그 PR이 고친 화면 파일의 주석).
- 견줄 때 보정 칸을 따로 본다. 보정을 빼고도 판정이 같은지 함께 적는다.
