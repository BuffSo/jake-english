# 시연 영상 만들기 (에뮬레이터 녹화)

> 작성: 2026-11-09 (demo-video 카드)
> 보충: 2026-11-09 (앱 그림이 바뀌었을 때, demo-jake-face 카드)
> 보충: 2026-11-10 (말 가운데 무음 틈과 잘린 말끝, demo-audio-cut 카드)
> 보충: 2026-11-10 (학습자 목소리를 바꿔 다시 찍을 때, demo-new-voice 카드)
> 보충: 2026-11-10 (다른 영상에 넣을 짧은 판, demo-short 카드)
> 영상, 원본 녹화, 학습자 목소리 녹음, 녹화하고 편집하는 스크립트는 저장소에 넣지 않고 비공개 폴더에 둔다. 학습자 목소리로 녹음을 만드는 명령과 이 맥의 경로는 비공개 메모에만 있다.

앱은 이 맥 서버에서만 돈다. 그래서 다른 사람에게 보여 줄 시연 영상을 따로 만든다. 이 문서는 시연 영상을 다시 만들 때 따를 기준, 순서, 겪은 문제를 담는다. 2026-11-09에 만든 영상은 1분 56초, 1920×1080이다. 2026-11-10에 소리를 고친 판은 1분 58초다. 같은 날 학습자 목소리를 바꿔 다시 찍은 판은 1분 53초다. 다른 영상에 넣으려고 그 판을 편집만으로 줄인 짧은 판은 1분 30초다. 순서는 첫 화면 → 자유 대화 → 대화 연습하기(목록 상황 하나와 끝 화면의 연습)다.

## 정한 기준

- **사용자의 실제 기록이 나오지 않게 한다.** 실제 서버(8787)의 데이터로 녹화하지 않는다. 지난 상황, 모아 둔 문장, 복습 탭에 사용자의 문장이 보이기 때문이다. 빈 데이터 폴더로 띄운 시험 서버를 옆 포트에 두고, 그 서버를 보는 앱을 따로 빌드한다. 끝나면 에뮬레이터에 원래 폴더의 main 앱을 다시 깐다.
- **폰이 아니라 이 앱 전용 에뮬레이터로 녹화한다.** 폰은 알림, 기기 이름, 통신사 표시가 나오고, 다른 카드와 나눠 써야 한다. 에뮬레이터의 상태 표시줄은 데모 모드로 시각 10:00, 알림 없음, 와이파이 가득으로 고정한다.
- **화면과 앱 소리는 scrcpy로 함께 담는다.** 라이언, 소희, 알림음이 화면과 같은 시각에 들어간다.
- **학습자 말은 미리 만든 녹음을 쓴다.** 에뮬레이터는 마이크 입력이 꺼져 있다. 학습자 목소리로 만든 녹음 파일을 두 곳에 쓴다.
  - 시험 서버가 앱이 보낸 무음 녹음 대신 그 파일을 받아쓴다(아래 「ffmpeg 감싸개」).
  - 영상에는 녹음한 자리에 그 소리를 섞는다.
  - 받아쓰기, 라이언과 소희의 답, 평가, 목소리는 모두 실제로 돈다.
- **기다리는 시간은 줄이고, 여는 글에 그렇다고 적는다.** 라이언이 생각하는 얼굴은 1초쯤만 남긴다.
- **화면은 16:9로 만든다(사용자).** 왼쪽에 폰 화면, 오른쪽에 장면 이름과 한두 줄 설명을 두고, 그 아래에 말 자막을 단다. 영어 말은 영어로, 한국어 말은 한국어로 단다. 소리 없이 봐도 따라갈 수 있게 하려는 것이다. 세로 9:16 초안은 노트북에서 양옆이 비고 자막이 폰 화면을 가려 고르지 않았다.
- **영상 속 글에는 앱 설명만 쓴다.** 여는 글은 앱 이름, 한 줄 소개, 「기다리는 시간은 줄였어요」다. 닫는 글은 앱 이름과 쓴 것 한 줄(안드로이드 앱, 맥 서버의 받아쓰기와 목소리, Claude)이다.
- **여는 글은 1.5초로 짧게 두고, 첫 프레임부터 보이게 한다.** 처음에는 3초였다. 사용자가 재생을 누르면 앱이 나오기 전에 쉼이 보인다고 짚었다. 소리 없는 글이 3초 이어지면 영상이 늦게 시작하는 것처럼 보인다. 이 영상은 따로도 쓰고 다른 영상 뒤에도 붙이므로, 어느 쪽에서도 바로 앱이 나오게 한다. 글은 서서히 나타나게 하지 않고, 끝 0.3초에만 어둡게 사라진다.
- **보는 사람의 눈은 폰 화면에 머문다.** 사용자가 영상을 보며, 폰 화면만 보느라 오른쪽 글을 하나도 못 읽었다고 했다. 그래서 앞뒤 장면을 잇는 말을 놓쳤다(앞에서 일부러 틀린 「go」와 돌아보기의 「went」). 오른쪽 글에 기대지 않고 폰 가까이에서 알린다.
  - 오른쪽의 큰 장면 제목은 카드 테두리와 같은 노랑으로 쓴다. 장면이 바뀌면 제목이 0.3초 동안 서서히 진해지며 6 % 커져 자리를 잡는다. 바뀌는 순간이 곁눈에 걸리되 튀지 않게 한다. 작은 설명 글과 말 자막은 그대로 둔다.
  - 이야기를 잇는 순간에는 폰 왼쪽에 노란 표, 폰 화면의 그 칸에 노란 테두리를 1.8초 둔다(0.2초에 나타나 0.25초에 사라진다). 2026-11-09 영상에서는 네 곳이다: 일부러 틀린 말의 말풍선, 소희 찬스 단추, 돌아보기에서 고친 문장, 평가가 짚은 낱말.
  - 표는 폰 오른쪽이 아니라 왼쪽에 둔다. 오른쪽에 두면 네 곳 가운데 세 곳에서 장면 설명이나 말 자막 상자를 가렸다. 폰 왼쪽 여백(250px)에 26px 굵은 글씨, 폰을 가리키는 작은 삼각형을 붙인다.
- **보여 줄 기능을 일부러 드러낸다.**
  - 자유 대화의 첫 답은 일부러 틀린다(「I go to …」). 대화 돌아보기에서 고칠 곳이 나온다.
  - 대화 연습하기는 한 줄에서 한 낱말을 바꿔 말한다(stop → step). 평가가 「stop이 step으로 들렸어요」라고 짚는다. 끝 화면의 「내 대사 다시 연습」에서 같은 줄을 바르게 말하면 「이번에는 stop도 대사대로 들렸어요」가 나온다.

## 순서

모두 원래 폴더가 아니라 이 일을 하는 worktree에서 한다. 포트는 다른 카드와 겹치지 않게 main 세션이 정한다(2026-11-09에는 8793, 8794).

1. **에뮬레이터를 띄우고 화면을 켜 둔다.**

   ```sh
   emulator -avd <이 앱 전용 AVD> -port 5556 -no-boot-anim -netdelay none -netspeed full &
   adb -s emulator-5556 shell svc power stayon true
   adb -s emulator-5556 shell cmd media_session volume --stream 3 --set 15
   ```

2. **시험 서버를 빈 데이터 폴더로 띄운다.** PATH 맨 앞에 ffmpeg 감싸개가 든 폴더를 둔다. 원래 폴더 서버(launchd)는 그대로 둔다(`DEVENV_맥서버_저절로_띄우기_20261107.md` 「launchd 서버를 멈추지 않고 시험하기」).

   ```sh
   PATH="<감싸개 폴더>:$PATH" JE_HOST=127.0.0.1 JE_PORT=8793 JE_WHISPER_PORT=8794 JE_DATA_DIR=<빈 폴더> \
     uv run python -m je_server >> <임시 폴더>/server.log 2>&1 &
   ```

3. **시험 서버를 보는 앱을 빌드해 깐다.** `app/.env`의 주소를 `http://127.0.0.1:8793`으로 바꿔 빌드한다(`app/README.md`). 깔기 전에 APK 안의 주소를 본다(`SPEECH_자유대화_기다림과_한국어_가르기_20261108.md` 「앱의 서버 주소를 바꿔 다시 빌드했는데 옛 주소가 남은 문제」). 에뮬레이터의 127.0.0.1을 맥으로 잇는다.

   ```sh
   adb -s emulator-5556 install -r app/android/app/build/outputs/apk/release/app-release.apk
   adb -s emulator-5556 reverse tcp:8793 tcp:8793
   adb -s emulator-5556 shell pm grant dev.jakeso.english android.permission.RECORD_AUDIO
   ```

4. **상태 표시줄을 고정한다.**

   ```sh
   adb -s emulator-5556 shell settings put global sysui_demo_allowed 1
   for c in "-e command enter" "-e command clock -e hhmm 1000" "-e command battery -e level 100 -e plugged false" \
            "-e command network -e wifi show -e level 4 -e fully true -e mobile hide" "-e command notifications -e visible false"; do
     adb -s emulator-5556 shell am broadcast -a com.android.systemui.demo $c
   done
   ```

5. **학습자 말을 만든다.** 학습자 목소리로 문장마다 m4a를 만들고, 시험 서버의 whisper(8794)로 받아써 낱말이 그대로 나오는지 본다. 다르면 다시 만든다(아래 「겪은 문제」). 한 문장은 4초 안팎으로 쓴다.

   ```sh
   ffmpeg -i line.m4a -ar 16000 -ac 1 -c:a pcm_s16le line.wav
   curl -s http://127.0.0.1:8794/inference -F file=@line.wav -F language=en -F response_format=json
   ```

6. **리허설을 한 번 한다.** 같은 시나리오를 끝까지 돌려 라이언의 답, 소희의 힌트, 평가 글을 본다. 자유 대화에서는 라이언의 답이 그때그때 다르다. 학습자의 다음 말은 그 답을 보고 고른다. 리허설 데이터는 다음 단계에서 버린다.
7. **본 녹화는 새 빈 데이터 폴더로 한다.** 리허설 폴더에서 세 가지만 옮긴다.
   - `audio/`: 서버가 만든 목소리라, 같은 글의 소리가 바로 나온다. 2026-11-09 대화 연습하기 부분을 이것 없이 다시 녹화하자, 라이언의 첫 평가가 세 토막으로 나왔다(사이 1.5초와 3.4초). 편집에서 잘라 냈다.
   - `tip.json`: 그날 섀도잉 한마디를 이미 한 것으로 둔다. 첫 화면에서 한마디가 길게 나오지 않는다.
   - `talk.json`: 자유 대화의 첫 질문 차례다. `{"next": 5}`면 「What did you do last weekend?」로 시작한다(`phrases.TALK_OPENERS`).

   시험 서버를 포트로 찾아 끄고, 새 폴더로 다시 띄운다.
8. **녹화한다.** 장면을 둘로 나눠(자유 대화, 대화 연습하기) 따로 담는다. 하나가 틀어져도 그것만 다시 찍는다.

   ```sh
   scrcpy -s emulator-5556 --no-window --audio-source=playback --audio-codec=flac --record=takeA.mkv &
   # 끝낼 때: kill -TERM <scrcpy pid>
   ```

   누를 때마다 맥의 시각을 파일에 남긴다. 「🎤 말하기」를 누른 시각이 학습자 말을 섞을 자리다. 감싸개의 대기열에는 그 장면에서 말할 녹음을 순서대로 넣는다.
9. **편집한다.**
   1. 녹화의 소리를 녹화 시계에 맞춘 wav로 먼저 뽑는다(아래 「녹화 소리의 시각을 그대로 따르자 말 가운데 무음 틈이 생기고 말끝이 잘렸다」). 그 wav에서 소리 구간을 찾는다(`silencedetect=n=-45dB:d=0.3`). 구간 찾기와 자르기가 같은 시계를 써야 한다. 구간마다 whisper로 받아써 무슨 말인지 붙인다. 누른 시각(녹화 시작 기준 + 0.09초)과 녹음 시작음이 같은 자리에 오는지 맞춰 본다. 2026-11-09에는 0.1초 안쪽으로 맞았다.
   2. 녹화마다 학습자 말을 녹음 시작음 0.3초 뒤에 섞는다(`adelay`, `amix`, 학습자 말 +3 dB). 바탕 소리는 1번의 wav를 쓴다. 30fps로 고친다.
   3. 남길 구간 목록(녹화, 시작, 끝)대로 자른다. 기다림, 쓰지 않는 화면, 겹치는 말은 뺀다. 구간마다 소리 앞뒤에 짧은 페이드를 건다.
      - 화면은 입력 쪽 `-ss`로 자른다. 소리는 섞은 파일을 처음부터 읽어 시각으로 자른다(`atrim=…,asetpts=PTS-STARTPTS`). 아래 「섞은 녹화를 `-ss`로 자르자 첫 구간 소리의 앞이 빠졌다」. `aresample=async`는 쓰지 않는다.
      - 구간 끝은 소리가 0으로 떨어진 뒤 0.05초 넘게, 화면이 다음으로 바뀌기 전에 둔다. 앱 목소리와 녹음 시작·끝 소리는 낱말이 끝나면 바로 디지털 무음이 되므로, 그 자리를 소리 크기로 찾는다. 앱이 한 대사를 여러 토막으로 냈으면 사이 기다림만 빼고 토막마다 끝까지 넣는다(사이에 0.4초쯤 쉼).
      - 구간 길이는 프레임 수에 맞춘다. 화면은 필터에서 `fps=30,trim=end_frame=<프레임 수>`로, 소리는 `apad`와 `atrim=duration`으로 같은 길이로 자른다. 아래 「구간 경계마다 소리에 짧은 틈이 생겼다」.
      - 앱이 막 뜨는 장면은 그림이 다 뜬 프레임부터 보인다. 아래 「첫 장면이 흰 화면과 빈 사진 자리로 시작했다」.
   4. 장면 설명과 자막은 그림(Pillow, Apple SD 산돌고딕 Neo)으로 그린다. 바뀔 때마다 1920×1080 한 장씩 만들고, 길이를 적은 concat 목록으로 배경 영상을 만든다.
   5. 폰 화면을 450×1000으로 줄이고 둥근 모서리 그림(`alphamerge`)으로 깎아 배경에 올린다.
   6. 첫 화면에서 카드를 고르는 장면은 눈에 띄게 한다(2026-11-09 사용자: 「자유대화를 선택하는 장면이 좀 눈에 뛰었으면 좋겠네」). 「자유 대화」와 「대화 연습하기」 두 장면에 같이 쓴다. 화면은 확대하지 않는다(아래 「카드 쪽 확대가 어색했다」).
      - 누르기 2.3초 전부터 남긴다. 오른쪽 설명을 「자유 대화를 골라요」처럼 고르는 말로 바꿔, 설명으로 바로 넘어가지 않고 한 번 쉰다.
      - 누르기 1.3초 전부터 카드에 노란 테두리를 0.6초 동안 서서히 그린다. 화면이 바뀌기 전(누른 뒤 0.08초)에 끈다. 늦게 끄면 바뀐 화면 위에 테두리만 떠 보인다.
      - 손가락(맥 이모지 👆를 그림으로 뽑은 것)이 0.95초 전에 오른쪽 아래에서 들어와, 0.4초 전에 가볍게 한 번, 누르는 순간에 한 번 더 찌른다(2026-11-09 사용자: 「누르는 표시 손가락 애니메이션이 쿡쿡 해도 되지 않나?」). 두 번째 찌를 때 흰 점과 퍼지는 동그라미를 그리고, 화면이 바뀐 뒤 사라진다.
      - 손가락이 카드 글자를 가리지 않게, 누르는 자리는 카드 글자 끝과 오른쪽 화살표 사이에 둔다. 카드마다 글자 길이가 달라 자리를 따로 정한다.
      - 누르는 순간은 녹화에서 화면이 바뀌는 프레임의 0.1초 앞이다. 카드 자리는 그 프레임 앞의 화면에서 카드 색으로 잰다.
      - 프레임을 뽑아 Pillow로 다시 그리고 그 구간에만 덮는다. 소리는 그대로 둔다. 덮은 뒤 앞뒤 프레임의 차이를 재어 경계에서 화면이 튀지 않는지 본다.
   7. 노란 표와 테두리(위 「보는 사람의 눈은 폰 화면에 머문다」)는 테두리와 표를 투명 그림 한 장으로 그리고, 그 시각에만 `fade=…:alpha=1`로 나타났다 사라지게 덮는다. 폰을 배경에 올리는 같은 ffmpeg에서 덮어 한 번 더 인코딩하지 않는다. 테두리 자리는 녹화 프레임에서 그 칸의 채움 색으로 잰다. 표가 구간 경계를 넘으면 그 칸이 양쪽 구간에서 같은 자리에 있는지 본다.
   8. 장면 제목이 바뀌는 곳은 0.3초 동안 프레임마다 배경 그림을 한 장씩 만들어 concat 목록에 넣는다(위 4번의 목록).
   9. 여는 글(1.5초)과 닫는 글(3초)을 붙이고 `loudnorm=I=-16:TP=-1.5:LRA=11`로 소리 크기를 고른다.
   10. 장면별 시각 표(시작, 끝, 장면, 자막, 노란 표)를 함께 남긴다. 다른 영상과 합치는 쪽이 이 표를 본다.
10. **정리한다.** 시험 서버를 포트로 찾아 끈다(`pkill -f je_server`는 쓰지 않는다). 받아쓰기 서버(8794)가 남았으면 그것도 포트로 끈다. 에뮬레이터의 `adb reverse`를 지운다. 데모 모드를 끄고(`-e command exit`) `svc power stayon false`로 되돌린다. 원래 폴더의 main 앱을 다시 깔고 에뮬레이터를 끈다. 시험 데이터 폴더(학습자 녹음이 든 `rec/`)는 에뮬레이터 시험이라 바로 지운다. 영상에 쓴 학습자 말과 원본 녹화만 비공개 폴더에 남긴다.

### ffmpeg 감싸개

시험 서버의 PATH 맨 앞에만 두는 `ffmpeg` 셸 스크립트다. 저장소에 넣지 않는다.

- 서버가 막 받은 녹음(`…/rec/….m4a`)을 16 kHz WAV로 바꿀 때(`-ar 16000`), 대기열 파일의 첫 줄에 적힌 학습자 말 파일을 그 녹음 위에 복사한다. 그다음 진짜 ffmpeg를 그대로 부른다.
- 녹음마다 한 번만 바꾼다. 바꾼 녹음의 경로를 적어 둔다. 「내 녹음」 사본을 만들 때 같은 녹음을 다시 변환하는데, 그때는 이미 학습자 말이라 그대로 둔다.
- 녹음 파일 자체를 바꾸므로 「🔊 내 녹음」에서도 학습자 말이 들린다. 녹음 대신 WAV만 바꾸던 2026-11-08 방법(`SPEECH_자유대화_기다림과_한국어_가르기_20261108.md` 「마이크가 꺼진 에뮬레이터에서 말하는 차례를 시험하기」)에서는 「내 녹음」이 무음이었다.
- 대기열이 비면 바꾸지 않고 기록에 남긴다. 그러면 무음이 받아쓰기로 가서 「잘 안 들렸어요」가 나온다.
- 감싸개는 자기 자리를 기준으로 대기열 폴더를 찾는다. 감싸개를 둔 폴더를 옮기면 대기열을 못 찾을 수 있다(아래 「감싸개가 대기열을 찾지 못해 첫 녹음이 무음으로 갔다」). 리허설의 첫 녹음 뒤에 감싸개 기록에 바꿔 넣은 줄이 있는지 본다.

## 학습자 목소리를 바꿨을 때 (2026-11-10 보충)

학습자 목소리를 만드는 기준 녹음을 바꿔, 같은 영상을 새 목소리로 다시 만들었다.

- **두 장면을 다시 녹화한다.** 앱 그림이 바뀔 때(아래)와 다르다. 학습자 말이 바뀌면 받아쓰기, 평가, 다음 답이 모두 그 말을 따라 바뀐다. 옛 녹화에 새 말만 섞으면 화면의 글과 소리가 어긋난다. 흐름, 장면 설명, 노란 표, 손가락, 여는 글은 그대로 두고 시각만 새 녹화에 맞춘다.
- **앱의 말은 녹화마다 다르다. 리허설에서 먼저 본다.**
  - 2026-11-10에는 자유 대화의 라이언 답과 소희 찬스의 첫마디가 지난번과 달랐다. 학습자의 둘째 말은 소희가 준 첫마디(「We ate…」)로 시작하게 바꿨다.
  - 보여 줄 두 가지는 리허설과 본 녹화 모두 그대로 나왔다. 대화 연습하기 평가는 stop이 step으로 들렸다고 짚었고, 대화 돌아보기는 과거형 went를 짚었다.
- **리허설의 `audio/`를 옮기면 목록 상황의 라이언 말이 누르자마자 나온다.** 상황을 누르는 순간, 라이언의 첫 말, 본보기가 한 구간이 됐고, 첫 평가도 한 토막으로 나왔다. 지난번에는 상황을 고른 뒤 몇 초를 기다렸고, 평가가 세 토막으로 나왔다(위 「본 녹화는 새 빈 데이터 폴더로 한다」).
- **학습자 말은 받아쓰기 모델 둘로 거른다.** 서버가 쓰는 모델(large-v3)이 글대로 들을 때까지 다시 만들고, 고른 판을 다른 모델(large-v3-turbo)로 한 번 더 받아쓴다.
  - turbo가 다른 낱말로 들은 판은 버린다. 2026-11-10에는 large-v3가 글대로 들은 판을 turbo가 「Line 4」를 「Lion 4」로 들어 다시 골랐다.
  - 지명은 두 모델이 함께 맞히는 판이 드물었다. 「Chungmuro」가 든 줄은 20판을 만들어도 둘 다 글대로인 판이 없었다(Chungmyo-ro, Jungmuro, Chumuro 등). 큰 모델은 글대로이고 turbo는 지명 철자만 다른 판을 쓴다. 서버의 평가는 큰 모델의 받아쓰기로 한다.
  - 「First」가 빠진 판도 이렇게 걸러진다.
- **the를 「더」로 읽은 판은 MFA로 고른다.** 사전에 the의 발음을 DH AH0(더)와 DH IY0(디) 둘만 두고 정렬한 뒤, 모음의 F2를 함께 잰다. 「더」는 F2가 1100~1300 Hz, 「디」는 1900 Hz 안팎이었다. 2026-11-10의 새 목소리는 받아쓰기를 통과한 14판 가운데 13판이 「더」였다.
- **앱을 띄운 뒤 첫 녹음에는 녹음 시작·끝 소리가 나지 않았다.** 누르는 딸깍 소리만 담겼다. 지난 녹화도 같았다. 둘째 녹음부터는 소리가 났다. 첫 녹음의 학습자 말은 딸깍 소리 0.3초 뒤에 섞는다.
- **앱이 낸 한 문장의 톤이 평소와 다르면 그 문장만 바꿔 넣는다.** 2026-11-10 사용자가 소희 찬스의 한 문장이 평소 소희와 다르게 들린다고 했다. 같은 목소리로 서버와 같은 길(같은 작업 프로세스, 빠르기)로 12판을 만들고 네 가지를 쟀다.
  - 기준 녹음과 닮은 정도: 작업 프로세스가 쓰는 목소리 검사와 같은 방법(3초 창의 화자 임베딩 코사인 최솟값).
  - 높이(F0 중앙값), 빠르기(초당 음절), 말 시작과 끝의 높낮이.
  - 녹화된 원래 문장은 다른 판보다 조금 느리고 높낮이 폭이 컸다. 닮음 점수는 한 판이 0.970으로 뚜렷이 높았고(나머지 0.951~0.960), 그 판이 높이와 말끝 모양도 지난 녹화의 소희와 가장 가까웠다.
  - 원래 문장 크기에 맞춰(+2.6dB) 그 자리에 넣었다. 화면 글은 그대로다. 사람이 고를 수 있게 고르지 않은 판과 평소 톤의 소희 대사를 비교 페이지에 나란히 둔다.
- **누른 시각은 딸깍 소리로 찾는다.** 에뮬레이터는 누를 때마다 0.09초짜리 딸깍 소리(-21 dB)를 낸다. 녹화에서 이 소리와 화면이 바뀌는 프레임은 0.05초 안쪽으로 맞았다. 맥에서 남긴 누른 시각은 녹화 시계와 녹화마다 -0.15초, +0.11초씩 어긋났다.

## 다른 영상에 넣을 짧은 판 (2026-11-10 보충)

시연 영상을 다른 영상 뒤에 붙이자 그 안의 시연이 길었다. 다시 녹화하지 않고 편집만 줄여 1분 53초를 1분 30초로 만들었다. 같은 대사를 두 번 연습하는 흐름, 라이언 답의 뒤 두 문장, 상황 고르기 안내 둘을 뺐다. 보여 줄 것(일부러 틀린 말 짚기, 소희 찬스, 대화 돌아보기, 평가, 다시 말해 나아진 점)은 모두 남겼다.

- **완성본은 그대로 두고 짧은 판을 따로 만든다.** 따로 틀 때는 완성본을 쓴다. 편집 도구를 복사해 구간, 자막, 내보내는 파일 이름만 바꾼다. 노란 표, 손가락, 장면 제목, 여는 글과 닫는 글은 완성본과 같다. 장면별 시각 표도 다른 이름으로 함께 남긴다. 합치는 쪽이 이 표에서 첫 장면 시작과 닫는 글 시작을 읽어 여는 글과 닫는 글을 잘라 낸다.
- **여러 화면을 건너뛸 때는 누르는 자리에서 자른다.**
  - 앱은 누르는 순간(에뮬레이터의 딸깍 소리) 한 프레임 안에 화면을 바꾼다. 라이언 안내는 0.1초쯤 뒤에 시작한다. 그래서 안내 없이 가운데 화면만 보여 줄 수 없다.
  - 앞 화면은 누르기 직전 프레임까지 두고, 뒤 화면이 나타나는 첫 프레임부터 잇는다. 그러면 자른 자리가 앱의 화면 바뀜과 겹쳐 따로 튀어 보이지 않는다.
  - 2026-11-10에는 「대화 연습하기」 카드를 누르는 순간 상황 목록으로 이었다. 주제 화면과 방법 화면, 그 두 안내가 빠졌다. 남긴 안내는 목록 화면 맨 위에도 쓰여 있는 「해 보고 싶은 상황을 골라 주세요.」다.
  - 첫 안내를 남기려면 아무것도 누르지 않은 주제 화면에서 목록으로 건너뛰어야 했다. 화면이 까닭 없이 바뀌어 보여 고르지 않았다.
  - 카드의 손가락과 누르는 표시는 자른 뒤에도 0.5초쯤 남는다. 완성본에서 다음 화면 위에서 끝났듯 이어진 화면 위에서 끝난다.
- **한 답의 앞 문장만 남길 때는 문장 사이 무음에서 자른다.** 앱 목소리는 문장 사이가 디지털 무음이다(2026-11-10에는 0.26초). 앞 문장이 0이 된 뒤 0.1초쯤에서 끊고, 말 자막도 그 문장만 남긴다.
- **새로 고른 구간의 첫 프레임과 마지막 프레임을 본다.**
  - 앱이 끝 화면을 띄울 때 화면이 두 프레임에 걸쳐 바뀌었다(빈 화면 → 더 하얀 빈 화면 → 끝 화면). 화면 바뀜 목록의 첫 바뀜을 끝 화면이 나온 자리로 읽고 그 시각부터 잇자, 완성본에 빈 흰 화면이 한 프레임 끼었다. 시작을 한 프레임 늦춰 고쳤다.
  - 구간의 시작과 끝은 편집이 자르는 섞은 녹화(30fps)의 프레임으로 맞춰 본다. 원본 녹화는 프레임 간격이 고르지 않아, 원본에서 뽑은 프레임과 한 프레임 어긋날 수 있다.
  - 자른 자리마다 완성본의 앞뒤 프레임을 번호로 뽑아 본다(`select='between(n,N-2,N+1)'`). `-ss`에 시각을 주면 소수점 오차로 옆 프레임이 뽑히기도 한다.
- **폰 화면은 구간 경계 몇 곳에서 한 프레임 늦게 바뀐다.**
  - 폰 화면을 배경에 올리는 단계(overlay)를 거친 영상에서, 그 자리의 폰 화면이 앞 구간의 마지막 프레임을 한 번 더 보였다. 2026-11-10 짧은 판의 새로 자른 세 자리 가운데 두 곳이 그랬다. 이어 붙인 폰 영상에서는 제 프레임에 바뀌었다.
  - 이어 붙인 폰 영상의 프레임 시각과 배경 프레임의 시각이 조금 어긋나는 것으로 보인다. 원인은 다 가리지 못했다. 완성본도 같은 단계를 거친다.
  - 소리와 배경은 제때 바뀌고 33ms라 그대로 두었다. 프레임을 볼 때 이것을 자른 자리의 잘못으로 읽지 않는다.
- **확인은 아래 「확인 방법」을 그대로 돌린다.**
  - 말 가운데 무음 틈 검사는 일부러 뺀 문장 앞에서 한 곳 걸린다. 무음이 구간 끝을 넘어, 뺀 문장이 있는 원래 소리까지 재기 때문이다. 구간 안의 원래 소리가 0인지 본다.
  - 다른 영상과 합치는 쪽의 소리 끊김 검사도 돌린다. 들어 볼 곳이 완성본에 있던 자리뿐인지 본다. 2026-11-10에는 완성본 15곳, 짧은 판 11곳이었고 새로 생긴 곳은 없었다.
  - 잘라 낸 자리마다 완성본과 짧은 판의 앞뒤 프레임, 파형, 소리를 나란히 놓은 비교 페이지를 만들어 사람이 볼 수 있게 한다.

## 앱 그림이 바뀌었을 때 (2026-11-09 보충)

- **다시 녹화하지 않는다.** 바뀐 그림이 영상에 나오는지부터 프레임으로 찾는다. 나오면 원본 녹화에서 그 자리에 새 그림을 덮고, 편집(9번)만 다시 돌린다.
- **2026-11-09 영상에 나오는 그림:** 첫 화면의 라이언 사진, 대화 돌아보기를 기다리는 동안 라이언의 생각하는 얼굴, 대화 연습하기 상황 화면의 라이언 듣는 얼굴, 소희 찬스의 소희 얼굴이다. 라이언이나 소희 그림을 바꾸면 이 자리를 고친다.
- **제이크 얼굴은 나오지 않는다.** 앱에서 제이크 얼굴은 상황 화면에서 「제이크에게 추천받기」를 골랐을 때만 나온다(추천을 확인하는 동안의 얼굴과 추천을 고르는 동안의 생각하는 얼굴, `app/src/ui/faces.ts`, `app/src/ui/thinking.ts`). 이 영상은 「목록에서 고르기」로 상황을 골랐다. 영상 속 제이크는 목소리와 말 자막으로만 나온다. 2026-11-09 제이크 그림을 반실사로 바꿀 때(`ASSET_제미나이로_얼굴_그림_만들기_20261106.md` 「앱 그림 바꾸기」) 찾아보고 알았다.
- **찾는 법:** 원본 녹화를 5fps, 1/4 크기로 뽑는다. 옛 그림을 앱이 보여 주는 크기로 줄이고 동그라미 안쪽 네모만 잘라, 프레임마다 정규화 상관(NCC)으로 맞춘다.
  - 동그라미 크기: 상황 화면 160dp, 기다림 96dp다. 이 앱 전용 에뮬레이터(1080×2400)에서는 420px, 252px였다. 첫 화면 얼굴 그림은 앱처럼 `FACE_BOX` 네모만 잘라 쓴다.
  - 영상에 나오는 것이 확실한 그림(라이언)도 같이 맞춰, 도구가 제대로 찾는지 본다. 같은 그림은 0.97 이상이었다. 옛 제이크 그림은 가장 높아도 0.69였고, 그 자리는 라이언 사진 위였다.
  - 다른 크기로 나올 수도 있으니 1fps로 120~900px 여러 크기도 한 번 맞춘다.
  - 이 맥에는 OpenCV가 없어 numpy의 FFT로 맞췄다. 새로 설치한 것은 없다.

## 겪은 문제와 해결

### scrcpy가 담은 소리가 원본보다 36 dB 작았다

- **증상:** 기본 설정(mp4, opus)으로 녹화하며 에뮬레이터에서 시험 소리를 틀었다. 담긴 소리의 가장 큰 값이 -37 dB였다. 원본은 -0.4 dB다. 에뮬레이터의 미디어 소리를 15/15로 올려도 같았다.
- **고친 것:** `--audio-codec=flac`으로 mkv에 담았다. 원본과 같은 -0.3 dB로 담겼다. `--audio-source=output`과 `playback`이 같은 값이었다.
- **원인:** 가리지 못했다. flac과 mkv로 바꾼 뒤로는 다시 작아지지 않았다.
- **막는 법:** 본 녹화 전에 10초쯤 시험으로 담아 `volumedetect`로 크기를 본다.

### 녹화하는 동안 앞에 떠 있는 앱을 못 찾았다

- **증상:** 누르기 전에 `dumpsys window | grep -m1 mCurrentFocus`로 이 앱이 앞에 있는지 본다. 녹화를 켜자 이 값이 `null`이 되어 스크립트가 누르지 않고 멈췄다.
- **원인:** 녹화하는 동안 포커스가 없는 디스플레이가 하나 더 있었다(`dumpsys window displays`의 `mDisplayId=7`). 그 디스플레이가 첫 줄로 나왔다. scrcpy가 만든 것으로 보인다.
- **고친 것:** `mCurrentFocus` 줄 가운데 `null`이 아닌 첫 줄을 본다.

### scrcpy가 SIGINT로 끝나지 않았다

- **증상:** `--no-window`로 띄운 scrcpy에 `kill -INT`를 보냈다. scrcpy가 그대로 녹화를 이어 갔다.
- **고친 것:** `kill -TERM`을 보낸다. 로그에 `Recording complete`가 찍히고 파일이 마무리된다.

### 시험 서버를 다시 띄우는 사이 에뮬레이터 화면이 꺼졌다

- **증상:** 첫 본 녹화에서 앱을 띄웠는데 화면이 꺼져 있어 누르기가 모두 멈췄다.
- **고친 것:** `svc power stayon true`. 녹화 전에 화면 상태(`dumpsys power`의 `mWakefulness=Awake`)를 본다.

### 와이파이 아이콘에 「!」가 붙었다

- **증상:** 데모 모드로 와이파이를 켜도 아이콘에 「!」가 붙었다. 인터넷이 안 되는 것처럼 보인다.
- **고친 것:** `network` 명령에 `-e fully true`를 더한다.

### 글로 찾아 누르기가 라이언 말 속의 같은 글자를 눌렀다

- **증상:** 「다음」 버튼을 화면 글로 찾아 눌렀다. 라이언의 평가 「… 다음 대사로 넘어가요」가 위에 있어 먼저 찾아졌고, 그 말풍선이 눌렸다.
- **고친 것:** 아래 버튼 줄의 「다음」, 「🎤 말하기」, 「말하기 끝」은 자리가 같아 고정 자리로 누른다. 같은 글이 여럿인 「자막 보기」는 마지막 것(가장 최근 말풍선)을 누른다.

### 학습자 목소리로 만든 말에서 whisper가 낱말을 빼고 들었다

- 이 절의 문장은 모두 목록 대본(`topics.py`의 「명동역에서 경복궁 가는 길」) 줄을 학습자 목소리로 합성한 것과, 그것을 받아쓴 글이다. 사용자가 말한 녹음이나 기록이 아니다.
- **증상:** 「Sure. First, take Line 4 one stop to Chungmuro.」를 만들어 받아쓰니 「Sure. Line 4-1 stop to …」로 「First, take」가 빠졌다. 「Take Exit 5. It goes …」는 「take exit, it goes …」로 5가 빠졌다. 그대로 쓰면 평가가 빠진 낱말을 짚는다.
- **고친 것:** 받아쓰기가 낱말 그대로 나올 때까지 다시 만든다. 대개 첫 번째나 두 번째에 맞았다. 숫자는 글자(4, four)를 같게 본다.
- 소리 하나를 바꾼 말(stop → step)은 다섯 번 만들어도 지명이 조금씩 다르게 받아써졌다(「Chungmyo-ro」). 평가는 지명을 짚지 않고 stop만 짚어 그대로 썼다. 리허설에서 평가 글을 먼저 본다.

### 편집한 구간의 소리가 1.5초 뒤 사라졌다

- **증상:** 첫 판 영상에서 첫 인사 뒤로 소리가 모두 없었다. 영상의 소리 구간을 받아써 보고 알았다.
- **원인:** 구간을 자를 때 `-ss`를 출력 쪽(`-i` 뒤)에 두고 `afade`를 걸었다. 필터는 원본 녹화의 시각을 보므로, 끝 페이드가 구간의 끝이 아니라 원본 시각으로 그 숫자에 걸렸다.
- **고친 것:** `-ss`와 `-t`를 입력 쪽(`-i` 앞)에 둔다. 다시 만든 뒤 구간마다 받아써 모든 말이 순서대로 있는지 봤다.

### 카드 쪽 확대가 어색했다

- **증상:** 고르는 장면을 눈에 띄게 하려고, 누르기 전에 화면 전체를 카드 쪽으로 2배 확대했다가 화면이 바뀐 뒤 풀었다. 사용자는 「자유대화를 줌해서 보이는거 되게 어색한데.. 줌까지는 그렇다쳐도 다시 전체로 돌아가니까 엄청 어색해」라고 했다. 확대한 동안에는 라이언 첫 질문의 자막 상자가 화면 끝에 반만 걸쳐 보여, 그동안 자막을 숨겨야 했다.
- **고친 것:** 확대를 뺐다. 누르기 전의 쉼과 고르는 말의 설명, 노란 테두리, 누르는 표시만 둔다. 사용자는 쉼이 있는 것만으로도 괜찮다고 했고, 버튼 강조를 다른 길로 들었다. 둘을 함께 썼다.
- **막는 법:** 화면 전체를 움직이는 효과(확대, 이동)는 들어갔다 나오는 두 번의 움직임이 생긴다. 앱 화면 안에서 표시하는 것을 먼저 쓴다.

### 첫 장면이 흰 화면과 빈 사진 자리로 시작했다

- **증상:** 첫 화면 장면이 시작하면 0.13초 동안 흰 화면, 이어서 라이언 사진 자리가 빈 회색 상자로 보였다. 사진이 0.4초에 걸쳐 서서히 나타났다. 앱이 뜨며 그림을 불러와 서서히 띄우는 모습이 녹화에 담긴 것이다. 여는 글 바로 뒤라 빈 화면이 이어지는 것처럼 보였다.
- **앞을 그냥 자르지 못한 이유:** 사진이 다 뜬 것은 녹화의 4.70초인데, 라이언 인사는 4.48초에 시작했다. 사진이 보이는 데서 자르면 인사 첫소리가 잘린다.
- **고친 것:** 소리는 인사 바로 앞(4.43초)부터 둔다. 화면은 사진이 다 뜬 첫 프레임(4.70초)을 그 앞 0.27초 동안 멈춰 보인다(`tpad=start_mode=clone`). 그동안 화면의 다른 곳(인사 글, 카드)도 함께 서서히 나타나는 중이었다. 그래서 멈춘 프레임은 앱이 바로 뜬 화면과 같아 보인다.
- **찾는 법:** 장면 앞의 프레임마다 마지막 프레임과의 차이를 사진 자리와 나머지로 나눠 잰다. 차이가 더 줄지 않는 첫 프레임을 고른다. 말이 시작하는 자리는 50ms마다 소리 크기를 재어 찾는다.
- **막는 법:** 앱이 막 뜬 화면에서 시작하는 장면은 첫 프레임들을 뽑아 그림이 다 떴는지 본다.

### 섞은 녹화를 `-ss`로 자르자 첫 구간 소리의 앞이 빠졌다

- **증상:** 위 문제를 고치다 알았다. 첫 구간의 소리가 녹화의 5.12초부터 들어 있었다. 구간은 4.2초(고친 뒤 4.43초)부터인데, 라이언 인사 앞 0.66초가 빠졌다. 그 자리는 소리의 시각 틈으로 남았다. 시각을 따르는 재생기는 그 틈을 0.9초 무음으로 틀고, 샘플을 이어 트는 재생기는 소리를 그만큼 당겨 틀 수 있다. 디코드한 소리 길이(116.1초)가 컨테이너 길이(117.4초)보다 1.3초 짧았다. 여는 글을 줄이자 이 틈이 인사 한가운데(2.99초)로 옮겨 갔다. 마지막 `loudnorm`이 소리를 모아 내보내기 때문으로 보인다.
- **원인:** 학습자 말을 섞어 다시 쓴 mkv(H.264 + PCM)를 입력 쪽 `-ss 4.2`로 자르면, 잘린 파일의 소리가 0.92초에서 시작했다. 원본 녹화를 같은 시각으로 자르면 0초에서 시작한다. 섞은 파일 안에서 소리 패킷이 화면보다 앞쪽에 놓여, 화면의 키프레임으로 찾아간 자리에서는 앞 소리를 이미 지나친 것으로 보인다. 녹화 앞쪽의 첫 구간만 그랬다.
- **고친 것:** 화면만 입력 쪽 `-ss`로 자른다. 소리는 같은 파일을 하나 더 열어 처음부터 읽고 시각으로 자른다(`atrim`). 이때 녹화의 소리 시각이 빈 곳(scrcpy, 0.05초 안팎)을 `aresample=async=1:min_hard_comp=0.01`로 무음을 채워 맞췄다. 이것이 말 가운데 틈을 만들어 2026-11-10에 바꿨다(아래 「녹화 소리의 시각을 그대로 따르자 말 가운데 무음 틈이 생기고 말끝이 잘렸다」).
- **찾는 법:** 잘린 구간마다 `ffprobe -show_entries stream=start_time`으로 소리 시작 시각을 본다. 0이 아니면 앞이 빠진 것이다. 영상의 소리 조각을 원본 녹화에 맞대어(파형의 상관) 어느 시각의 소리인지 찾았다.

### 구간 경계마다 소리에 짧은 틈이 생겼다

- **증상:** 위를 고친 뒤에도 최종 파일의 AAC 패킷 가운데 11개가 제 길이(1024 샘플, 21.3ms)보다 16~50ms 길었다. 모두 구간 경계 뒤였고, 합쳐 0.29초였다.
- **원인:** 구간 길이가 프레임의 배수가 아니었다(예: 4.85초 = 145.5프레임). 화면은 146프레임으로 반올림되고 소리는 4.85초 그대로라, 이어 붙일 때 소리에 틈이 생겼다. 시작 시각이 프레임 사이에 걸린 구간은 길이가 프레임의 배수여도 한 프레임이 더 나왔다.
- **고친 것:** 구간 길이를 `round(길이 × 30) / 30`으로 정한다. 화면은 필터에서 `fps=30,trim=end_frame=<프레임 수>`로 자르고, 소리는 `apad`와 `atrim=duration`으로 같은 길이로 자른다. 자막과 장면 시각도 이 길이로 쌓는다.
- 처음에는 출력 쪽 `-frames:v`로 화면을 잘랐다. 그 프레임에서 파일 쓰기가 끝나, 네 구간의 소리 꼬리가 0.04~0.08초 잘렸다. 구간마다 화면 프레임 수와 소리 길이를 견주어 찾았다.
- **찾는 법:** 아래 「확인 방법」의 소리 틈 확인.

### 녹화 소리의 시각을 그대로 따르자 말 가운데 무음 틈이 생기고 말끝이 잘렸다

- **증상:** 이 영상을 다른 영상 뒤에 붙여 들어 보던 사용자가, 라이언 평가의 말끝(「…알아들었어요」의 「어요」, 「한 번 더 해 볼까요」의 「까요」)이 잘린 것을 들었다. 세 토막의 끝이 0.24~0.30초씩 잘려 있었다. 찾아보니 다른 구간 끝도 여러 곳이 말끝의 꼬리나 녹음 끝 소리를 0.17초까지 잘랐다. 학습자 말 한 줄 안에는 10~50ms 디지털 무음 틈이 여섯 번 있었고, 영상 전체로는 21곳이었다. whisper는 잘린 낱말도 온전히 받아써 이것을 잡지 못했다.
- **원인 1, 말 가운데 틈:** scrcpy는 소리 패킷(4096 샘플, 85ms)마다 기기에서 읽은 시각을 붙인다. 이 시각이 ±60ms 흔들린다. 한 패킷이 늦고 뒤 패킷들이 몰려 오는 식이고, 학습자 말을 녹음하는 동안 특히 심했다. 진짜로 소리가 빈 곳은 두 녹화를 통틀어 한 번(216ms, 녹음을 시작하기 1초쯤 전의 무음)뿐이었다. 위에서 시각을 지키려고 건 `aresample=async=1:min_hard_comp=0.01`은 늦은 시각마다 무음을 끼우고 이른 시각마다 샘플을 버렸다. 학습자 말은 그 앞 단계에서 섞었으므로 같이 끊겼다. 학습자 말 파일 자체는 멀쩡했다.
- **원인 2, 잘린 말끝:** 구간 시각은 녹화의 소리 샘플을 그냥 이어 붙여 잰 시각(소리 구간을 찾는 도구)으로 골랐다. 이 시각은 녹화 시계보다 첫 패킷 시각(0.08초)만큼 앞서고, 진짜 빈 곳 뒤로는 0.30초 앞선다. 빌드는 소리를 녹화 시계로 자르므로 구간 끝이 그만큼 일찍 와서 말끝이 잘렸다. 여유를 그보다 적게 둔 구간 끝이 걸렸다. 학습자 말도 같은 이유로 적은 시각보다 0.1~0.4초 늦게 나왔다.
- **고친 것:**
  - 녹화의 소리를 끊지 않고 녹화 시계에 맞춘 wav를 먼저 만든다. 패킷마다 (붙은 시각 − 샘플 수로 센 시각)을 구하고, 그 패킷부터 끝까지의 최솟값을 진짜 어긋남으로 본다. 시각은 늦게 붙을 수는 있어도 일찍 붙지는 않기 때문이다. 어긋남이 늘어난 만큼의 무음은 다음 조용한(-60dB 아래) 패킷 경계에 넣는다. 그러면 말 가운데는 샘플이 이어지고, 진짜 빈 곳만 무음으로 채워진다. wav는 녹화 0초부터 시작한다(첫 패킷 시각만큼 앞에 무음).
  - 학습자 말과 바꿔 넣은 말은 이 wav에 섞는다. 그다음 단계에서 `aresample=async`를 쓰지 않는다.
  - 소리 구간을 찾는 도구도 이 wav로 잰다. 찍힌 시각이 자르는 시각과 같아진다.
  - 잘린 구간 끝 14곳을 위 「편집한다」의 구간 끝 규칙대로 옮기고, 화면이 바뀌는 프레임과 겹치지 않는지 원본 녹화의 화면 변화로 봤다. 라이언 자막도 목소리가 시작하는 자리로 옮겼다(0.30초).
  - 자막과 장면 시각은 프레임으로 맞춘 구간 끝으로 자른다. 처음 쓴 끝(예: 58.5프레임)으로 자르자 자막 줄이 다음 구간으로 0.02초 넘어갔다.
- **확인:** 녹음 시작·끝 소리와 화면이 바뀌는 프레임 사이가 여덟 곳 모두 원본 녹화와 한 프레임(33ms) 안으로 같았다. 학습자 말 다섯 줄은 원래 말 파일과 같은 파형이었다(100ms마다 크기를 맞춘 일치도 중간값 17~21dB. 고치기 전 판에는 중간값이 -18dB인 줄도 있었다). 길이는 2.3초 늘었다.
- **막는 법:**
  - scrcpy 녹화의 소리 시각을 그대로 믿지 않는다. 먼저 (패킷 시각 − 샘플 수로 센 시각)을 패킷마다 찍어, 흔들림과 진짜 빈 곳을 나눈다.
  - 구간을 고르는 도구와 자르는 도구가 같은 시계를 쓰게 한다.
  - 말끝은 받아쓰기로 확인되지 않는다. 아래 「확인 방법」의 말 가운데 무음 틈 검사와 구간 끝 검사를 돌린다.

### 연습 앞에서 「Sure.」가 두 번 들렸다

- **증상:** 끝 화면에서 「내 대사 다시 연습」을 누른 구간에 라이언 본보기의 첫 낱말 「Sure.」가 들어갔다. 바로 뒤에 학습자가 「Sure. First, …」를 말해 겹쳐 들렸다.
- **고친 것:** 그 구간을 뺐다. 구간을 자를 때 받아쓴 소리 구간과 맞대어, 말이 반만 들어가는 자리를 피한다.

### 마이크가 꺼진 에뮬레이터에서는 녹음이 5초 뒤 취소되지 않았다

- 폰에서는 「🎤 말하기」를 누르고 5초 동안 말소리가 없으면 녹음을 버린다(`APP_녹음_중_알리기_20261108.md`). 마이크 입력이 꺼진 에뮬레이터에서는 20초 넘게 녹음이 켜져 있었다. 녹음 중 목소리 줄도 움직이지 않는다.
- 그래서 학습자 말이 4초를 넘어도 「말하기 끝」을 말이 끝난 뒤에 누를 수 있다. 영상에서는 목소리 줄이 움직이지 않는 것이 한계다.

### 감싸개가 대기열을 찾지 못해 첫 녹음이 무음으로 갔다

- **증상:** 2026-11-10 리허설의 첫 녹음에 라이언이 「잘 안 들렸어요. 한 번 더 말해 줄래요?」라고 답했다. 감싸개 기록 파일도 생기지 않았다.
- **원인:** 감싸개는 자기 파일 자리에서 한 폴더 위의 `demo/`를 대기열 폴더로 본다. 이번에는 편집 도구 폴더를 통째로 복사해 감싸개가 한 단계 더 깊이 들어갔다. 그래서 없는 폴더를 보았고, 바꿔 넣지 못한 무음이 받아쓰기로 갔다.
- **고친 것:** 감싸개가 두 자리를 모두 찾게 했다. 그때는 서버를 다시 띄우지 않고, 감싸개가 찾는 자리에 대기열 폴더를 잇는 링크를 두었다.
- **막는 법:** 리허설 첫 녹음 뒤에 감싸개 기록에 「바꿔 넣음」 줄이 있는지 본다.

### 완성본 받아쓰기가 앱 목소리의 한 낱말을 다르게 들었다

- **증상:** 대화 돌아보기의 라이언 설명 「과거형 went를 써야 해요」를 완성본에서 받아쓰니 「멘트를」로 나올 때가 많았다. 같은 자리를 원본 녹화에서 받아쓰면 두 모델 모두 「웬트를」이었다.
- **찾은 것:** 편집 단계마다(섞은 녹화, 구간, 이어 붙인 것, 노란 표를 덮은 것) 받아쓰니 모두 「웬트」였다. 마지막 단계의 AAC 인코딩에서 바뀌었다. 소리 크기를 바꾸거나 `loudnorm`만 걸어서는 바뀌지 않았다. 그 문장만 잘라 AAC로 바꾸면 「웬트」였다.
- **판단:** 소리 경계에 걸린 낱말이라, 인코딩의 작은 차이로 받아쓰기가 갈린다. 앱이 낸 소리를 그대로 두었다. 바꿔야 하면 같은 문장을 서버와 같은 길로 다시 만들어 그 한 마디만 바꿔 넣는다(v6의 「go는」처럼). 정하는 것은 사람이 들어 본 뒤다.
- **막는 법:** 완성본 받아쓰기가 원본과 다르면 바로 편집을 의심하지 말고, 단계별로 받아써 어디서 바뀌는지 먼저 본다.

### 마지막 합치기에서 소리 전체가 8비트가 되어 작은 소리가 0이 됐다

- **증상:** 시연 영상을 다른 영상 뒤에 붙인 쪽이 원본 녹화와 맞대어 보니, 원본에서 -46~-64dB였던 작은 소리가 완성본에서 5~40ms 동안 완전히 무음이 된 곳이 20~25곳 있었다. 말의 조용한 곳(자음 사이, 말끝)이다. 2026-11-09 첫 판부터 있었다.
- **원인:** 마지막 단계에서 여는 글과 닫는 글의 빈 소리(`anullsrc`)와 본편 소리를 `concat` 필터로 이었다. 형식을 정하지 않자 ffmpeg가 이 필터의 소리 형식으로 u8(8비트)을 골랐다. 프로그램 전체가 8비트로 지나가며 -48dB 아래가 0이 됐다. 이어 붙인 소리를 PCM으로 뽑아 보면 모든 샘플이 256의 배수였다.
- **찾은 순서:** 편집 단계마다 같은 검사를 돌렸다. 본편을 다 만든 소리에는 구멍이 없었고, 여는 글과 닫는 글을 이은 직후(크기 맞추기와 AAC 전)에 생겼다. `loudnorm`, AAC, 고정 크기와 리미터로 바꿔 봐도 그대로여서, 그 앞의 잇는 단계를 의심했다.
- **고친 것:** `concat`에 들어가는 모든 소리에 `aformat=sample_fmts=fltp`를 건다. 편집이 만든 구멍이 0곳이 됐고, 크기(-16.7 LUFS)와 길이는 그대로였다.
- **막는 법:** 빈 소리를 만드는 필터와 다른 소리를 한 필터에 넣을 때는 형식(sample_fmts)을 정한다. 아래 「확인 방법」의 짧은 구멍 검사를 원래 소리 -45dB 기준에 더해 -60dB까지 본다.

### 이 맥의 ffmpeg에는 글을 그리는 필터가 없다

- homebrew ffmpeg에 `drawtext`, `subtitles`, `ass` 필터가 없다. 글은 Pillow로 그림을 만들어 덮는다. 새로 설치한 것은 없다.

## 확인 방법

- **소리 틈:** `ffprobe -select_streams a -show_entries packet=pts_time,duration_time`으로 AAC 패킷마다 길이를 보고, 1024 샘플보다 긴 것이 없는지 본다. 소리를 끝까지 디코드한 길이가 컨테이너 길이와 같은지도 본다.
- **싱크:** 녹음 시작음(소리)과 「말하기 끝」 화면이 나오는 프레임의 차이가 원본 녹화와 같은지 본다. 2026-11-09 녹화에서는 원본, 고치기 전 영상, 고친 영상 모두 0.12~0.15초였다. 원본 녹화의 소리는 녹화 시계에 맞춘 wav로 잰다. 샘플을 이어 붙인 소리로 재면 진짜 빈 곳 뒤로 0.3초 어긋나 보인다.
- **말 가운데 무음 틈:** 원래 소리(녹화 시계에 맞춘 wav에 학습자 말을 섞은 것)를 만든다. 만든 영상에서 5ms 넘게 디지털 무음인 곳마다, 같은 시각의 원래 소리가 -45dB보다 큰지 본다. 크면 편집이 만든 틈이다. 앱 목소리는 낱말 사이가 원래 무음이고, AAC는 -55dB 아래 꼬리를 0으로 만들기도 해서, 영상만 보고 찾으면 정상인 곳이 많이 걸린다. 2026-11-10에 21곳에서 0곳이 됐다. 같은 날 다시 찍은 판도 0곳이었다. 한 곳이 걸렸는데, 일부러 뺀 본보기가 시작하기 직전에 자른 구간 끝이라 편집이 만든 틈이 아니었다. 무음이 구간 경계를 넘는지 함께 본다.
- **짧은 구멍:** 위 검사는 원래 소리가 -45dB를 넘는 곳만 봐서, 작은 소리가 0이 된 곳을 놓쳤다(위 「마지막 합치기에서 소리 전체가 8비트가 되어 작은 소리가 0이 됐다」). 완성본을 5ms 창으로 재어 -70dB 아래가 40ms 이하로 끼어든 곳마다, 원본 녹화의 같은 소리(상관으로 찾는다) 크기를 본다. 원본이 -60dB보다 크면 편집이 만든 구멍이다. 2026-11-10 고친 뒤 0곳이었다.
- **구간 끝:** 구간마다 원래 소리의 마지막 60ms 크기와, 끝난 뒤 0.3초 안에 소리가 이어지는지 본다. 이어지면 그 소리가 일부러 뺀 다음 문장인지 받아써 확인한다.
- **소리:** 만든 영상의 소리 구간을 찾아 구간마다 whisper로 받아쓴다. 첫 화면 인사부터 마지막 평가까지 말이 순서대로 다 있는지 본다. 학습자 말이 녹음 화면(「● 말하기 끝」)과 같은 자리에 있는지 본다.
- **화면:** `fps=1/4`로 4초마다 한 장씩 뽑아 한 장에 모아 본다. 장면 설명과 자막이 화면과 맞는지, 폰 화면에 사용자 기록이 없는지 본다.
- **크기:** `ebur128`의 통합 크기가 -16 LUFS 근처인지 본다. 2026-11-09 영상은 -16.7 LUFS, LRA 6.5 LU였고, 같은 날 편집을 고친 판은 -16.6 LUFS, LRA 6.8 LU였다. 2026-11-10 다시 찍은 판은 -16.7 LUFS였다.
- **비용:** 리허설과 본 녹화를 합쳐 API 비용이 20센트 안쪽이었다. 목록 상황은 대본을 만들지 않아, 평가와 자유 대화의 답, 소희 찬스, 대화 돌아보기에만 든다.
