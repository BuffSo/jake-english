# PROMPT 일마다 모델을 견줘 고르기

> 2026-11-08 quick-model-review 카드에서 정하고 겪은 것

Claude를 부르는 일마다 어느 모델(Haiku, Sonnet)을 쓸지 정할 때의 기준과 방법이다. 이 앱에서는 짧은 말 모델 하나(Haiku)가 소희 통역, 제이크 추천, 라이언 평가를 함께 맡았다. 세 일을 견줘 보니 결과가 일마다 달라서 추천만 Sonnet으로 바꿨다(`server/README.md` 「Claude 모델 고르기」).

## 정한 기준

- **일마다 따로 견준다.** 한 모델이 맡은 일이라도 결과가 다르다. 이번에는 추천만 Sonnet이 확실히 나았다. 통역과 평가는 비슷했는데 Sonnet이 느렸다. 모델을 한꺼번에 바꾸는 설정 하나로 정하지 않는다.
- **같은 입력을 두 모델에 번갈아 묻는다.** 입력마다 묻는 순서를 바꾼다. 그래야 몇 분 동안 API가 느려져도 두 모델이 똑같이 영향을 받는다. 추천은 예외다. 거절 목록이 모델마다 제 답으로 이어져 첫 번째 뒤로는 입력이 갈리므로, 한 모델씩 차례로 돈다. 그래서 추천의 기다림은 몇 분 차이를 두고 잰 값이다.
- **입력은 지어낸다.** 사용자의 지난 기록 문장, 녹음 받아쓰기, 연습 자료의 대본은 쓰지 않는다(`REVIEW.md` 「공개 저장소 노출」). 지어낸 입력의 답은 devlog와 PR에 예로 옮겨도 된다.
- **서버가 실제로 보내는 조건을 살린다.** 시험 입력이 서버의 입력보다 쉬우면 실수가 드물게 나온다. 이번에 최근 상황을 둘만 보냈을 때는 Haiku의 이상한 추천이 21번 중 2~3번이었다. 서버처럼 열 개를 보내자 7번으로 늘었다. 앞 카드의 추천 스크립트는 최근 상황을 하나도 보내지 않아서, 실제 서버에서만 나온 실수(「끝말:」 따라 쓰기)를 한 번도 보지 못했다.
- **틀리기 쉬운 것을 섞는다.** 통역이면 숫자(값, 층, 시각, 승강장), 길 안내, 관용 표현, 짧은 대답(「Not at all」처럼 뜻이 뒤집히는 것)을 넣는다. 사람이 고쳐 써 둔 통역(목록 대본)은 견줄 필요가 없다. 차이는 써 두지 않은 통역에서 난다.
- **품질은 직접 읽고 정한다.** 점수 매기는 모델을 따로 쓰지 않는다. 기계 검사(`rec_flags`, `check_ryan_wording.flags`)는 알려진 실수만 가리킨다. 이번에 Sonnet 통역이 「ten and a half」를 「270 반 사이즈」로 바꾼 것도, 추천의 다양함도 읽어서 찾았다.
- **기다림은 사용자가 기다리는 지점에서 잰다.** 흘려 보내는 답(평가)은 첫 글자와 첫 문장까지 걸린 시간을 잰다. 목소리가 첫 문장부터 나오기 때문이다. 다 받고 쓰는 답(통역, 추천)은 끝까지 걸린 시간을 잰다.
- **값은 claude-api 스킬로 확인한다.** 기억으로 쓰지 않는다. 2026-11-08 기준 백만 토큰당 입력과 출력은 Haiku 5.5가 0.10달러와 0.50달러, Sonnet 5.5가 2달러와 10달러다. 늘어나는 값은 하루 쓰는 만큼으로 어림해 함께 낸다(이번에는 추천 5번, 통역 10번, 평가 30번으로 셈했다).
- **모델은 서버가 고를 수 있는 설정 그대로 견준다.** 이 앱의 Sonnet 짧은 말 설정은 생각하는 단계 끔(`between_tools`)이고 effort를 보내지 않는다(`claude.QUICKS`). 다른 설정으로 견주면 바꾼 뒤의 서버와 다르다.

## 명령

맥 서버 폴더(`server/`)에서 돌린다. 모두 돈이 드니 몇 번 부르고 얼마인지 먼저 알린다.

| 명령 | 하는 일 | 값 |
|---|---|---|
| `uv run python scripts/compare_quick_models.py [--only interpret\|recommend\|feedback] [--runs N] [--presses N] [--seed N] [--out 파일]` | 세 일을 두 모델에 같은 지어낸 입력으로 묻는다. 답을 모두 찍고, 일과 모델마다 시간, 걸림, 값을 요약한다 | 기본 138번에 27센트쯤 |
| `uv run python scripts/check_jake_recommend.py [--model haiku\|sonnet]` | 추천 하나만 서버 조건(지어낸 최근 상황 열 개)으로 스물한 번 받는다. 끝말을 지켰는지 센다 | Sonnet 6.5센트, Haiku 0.3센트 |
| `uv run python scripts/check_ryan_wording.py --only feedback --quick haiku\|sonnet` | 평가만 지어낸 열두 경우로 받아 어긴 규칙을 표시한다 | 한 번에 몇 센트 |
| `scripts/try_recordings.py` | 학습자 목소리 녹음을 서버에 보내 받아쓰기부터 첫 소리까지 잰다(`DEVENV_폰없이_녹음_시험하기_20261108.md`) | 녹음마다 한 번 |

- 서버 전체로 재려면 원래 폴더 서버를 멈추지 않고 worktree 서버를 옆 포트에 띄운다. `JE_CLAUDE_QUICK`나 `JE_CLAUDE_RECOMMEND`를 바꿔 가며 다시 띄운다(`DEVENV_맥서버_저절로_띄우기_20261107.md` 「launchd 서버를 멈추지 않고 시험하기」). 로그의 `claude models: writer …, quick …, recommend …` 줄로 어느 모델인지 확인한다.

## 겪은 문제와 해결

### 최근 상황을 적게 보내 실수를 덜 봤다

- **증상:** 지어낸 최근 상황 둘과 함께 보냈을 때 Haiku의 이상한 추천은 21번 중 2~3번이었다. 실제 기록(최근 열 개)으로 서버에서 받은 넷 중 둘은 지시문 말투를 그대로 말했다(「…상황과 다른 상황에서, …」, 「저는 이번에 제안할 상황은 …」).
- **원인:** 서버는 그 주제의 최근 상황 열 개를 보낸다(`store.recent_situations`). 메시지가 길고 받아들인 추천 문장(끝말이 붙은 것)이 많을수록, 모델이 받은 글을 따라 쓰거나 그 글에 대해 말했다.
- **고친 것:** 지어낸 최근 상황을 주제마다 열 개 두고(`check_jake_recommend.RECENT`), 두 스크립트가 같이 쓴다. 다시 견주니 Haiku는 21번 중 7번, Sonnet은 0번이었다.
- **같은 실수를 막는 법:** 견주기 입력은 서버가 그 일에 보내는 메시지를 그대로 만들어 본다. 무엇을 함께 보내는지(최근 기록, 거절 목록, 앞뒤 대사) 코드에서 먼저 읽는다.

### 녹음 시험이 찍은 대사와 녹음이 간 대사가 달랐다

- **증상:** 녹음 시험에서 라이언이 대사에 없는 낱말을 짚었다. 모델이 지어낸 것으로 볼 뻔했다. 같은 입력을 모델에 직접 보내면 바르게 말했다.
- **원인:** `try_recordings.py`는 원본 역할극의 대사를 찍고 복사본에 녹음을 보낸다. PR #44부터 목록 상황의 복사본은 지금의 목록 대본을 쓴다. 그런데 원본은 대본이 바뀌기 전에 연습한 것이라, 두 대사가 달랐다. 맥은 복사본의 대사로 바르게 짚었다.
- **어떻게 알았나:** `--keep`으로 복사본을 남겨 저장된 시도의 짚을 것과 대사를 열어 봤다.
- **같은 실수를 막는 법:** 모델 탓으로 보기 전에 모델에 간 입력을 먼저 본다. 저장된 시도의 `issues`나 서버가 만든 입력을 그대로 모델에 다시 보내 같은 답이 나오는지 본다. 스크립트를 고치는 일은 할 일 `20261108_25_todo_try_recordings_copy_line.md`로 남겼다.

### 첫 소리 시간은 모델보다 소리 저장소에 달렸다

- **증상:** 서버의 평가 첫 소리가 같은 모델에서도 1.7초에서 5초까지 갈렸다.
- **원인:** 첫 문장(「나머지 낱말은 다 알아들었어요.」 같은 것)의 소리가 이미 맥에 있으면 바로 나오고, 새 문장이면 목소리를 만드는 시간이 더해진다. 모델이 그 문장을 조금만 바꿔 말해도 새 소리를 만든다.
- **같은 실수를 막는 법:** 모델끼리 기다림을 견줄 때는 첫 글자와 첫 문장까지의 시간을 쓴다. 첫 소리는 목표(4~5초)를 넘는지만 본다.
