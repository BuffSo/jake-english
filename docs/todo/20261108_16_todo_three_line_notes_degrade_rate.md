## 왜 하나

2026-11-08 사용자가 폰에서 말로 정한 상황으로 역할극을 했다. 내 대사 세 줄의 읽는 법이 모두 세 번 만든 끝에 기계 검사를 통과하지 못해 덜 된 채 남았다(`three-line note degraded after 3 tries`). 둘은 읽는 법 설명이 빠졌고(`ref`), 하나는 센 음절 표시 일부가 빠졌다(`hi`). 줄마다 14~15초, 글쓰기 모델(Sonnet)을 세 번씩 불렀다.

맥 서버 로그 전체(2026-11-08 오전까지)를 세어 보니 읽는 법 165개 가운데 48개(29%)가 덜 된 채 남았다. 통과한 117개도 한 번에 된 것은 59개, 두 번 45개, 세 번 13개다. 덜 된 이유는 `ref`(설명의 [[…]]가 한글 줄의 음절과 맞지 않음)가 가장 많고, `hi`(센 음절 표시), `words`, `stress`가 뒤따른다.

PR #36으로 내 대사는 읽는 법을 기다리지 않고 먼저 보이지만, 덜 된 읽는 법은 「읽는 법 보기」에서 설명이 빠진 채 보이고, 다시 만드는 만큼 돈과 맥의 시간이 든다. PR #34의 목록 대본은 한 번 만든 읽는 법을 회차마다 다시 쓰니, 덜 된 것이 굳는다(한글이 하나도 없는 것만 다시 만든다).

## 할 일

1. 덜 된 이유별로 실제 예를 모아(공개 파일에는 지어낸 예만) 원인을 본다. `ref`가 지시문의 설명 규칙 때문인지, 검사(`threeline.py`)가 너무 엄한지부터 가른다.
2. 고치는 쪽을 정한다: 지시문(`prompts.THREE_SYSTEM`)을 고치기, 검사를 맞게 고치기, 덜 된 부분만 고쳐 달라고 한 번 더 묻기(전체를 다시 만들지 않기) 가운데 고르고, 같은 문장으로 고치기 전과 뒤의 통과율과 호출 수를 잰다. 실제 모델 호출 수와 비용은 먼저 한 줄로 알린다.
3. 목록 대본의 읽는 법은 덜 된 것이 굳지 않게, 고친 뒤 한 번 다시 만들지 정한다.
4. 함께 볼 것: `20261108_11_todo_line_notes_minors.md`, 가이드 `docs/guide/` 의 세 줄 관련 절, 역할극 뒤 연습 스펙의 세 줄.
